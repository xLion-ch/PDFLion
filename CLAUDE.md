# PDFLion

A PDF viewer for macOS (Apple silicon and Intel), Windows and Linux (Ubuntu and Linux Mint): Mozilla's [pdf.js](https://github.com/mozilla/pdf.js) generic viewer in Electron. pdf.js renders and provides the viewer UI. The Electron shell stays thin, and adds what a browser tab can't: opening files from the file manager, a home screen of recent documents, native menus and shortcuts, tabs that move between windows, saving in place, installers, and updates from GitHub releases.

A web app for the iPad (`src/web/`, see The web app) runs the same viewer, Home and tab strip in the browser, with a shell page where Electron's main process would be, and works offline once it has run. GitHub Pages serves it at `https://xlion-ch.github.io/PDFLion/`, deployed with each release.

[README.md](README.md) covers installing, building, releasing, and the checks by hand before merging into `main`, since every push there is a release.

## Ground rules

- **Never commit.** Not even when a task says to. Leave the changes in the working tree, stage them if asked, and suggest a commit message. The user commits.
- **Never edit `vendor/pdf.js/`**, a submodule pinned to a release tag. Customise it from outside:
  - `src/viewer/bridge.js`, a main-world script that sets `PDFViewerApplicationOptions` and drives `PDFViewerApplication`
  - `src/viewer/overrides.css`, which restyles the viewer in Material Design 3, with Material Symbols icons from `src/viewer/icons/`
  - `src/viewer/geometry.js`, the eraser's geometry, which touches nothing in pdf.js

  `src/main/protocol.js` injects them into `viewer.html` as it serves it, and `scripts/build-web.js` into the web app's copy. If something seems to need a pdf.js patch, look for a way through those first, and if there is none, stop and ask.
- Prefer pdf.js's built-in behaviour over reimplementing it.
- `bridge.js` is the only code that touches pdf.js internals (`PDFViewerApplication`, its `eventBus`, `AppOptions`). They change between releases, so check every name against the pinned sources, such as `vendor/pdf.js/web/app.js` and `web/app_options.js`, never from memory.
- Its hosts give it `window.pdflion`: the desktop's `preload.cjs`, and the web app's `viewer-host.js`. Home's give `window.pdflionHome`: `home.cjs` and `home-host.js`. The hosts never touch pdf.js, and `bridge.js` adds what a host offers, by the members it has.
- Follow each platform's conventions. On all three, each document gets a tab in PDFLion's own tab strip, in the frontmost window.
  - macOS: the menu bar, ⌘ shortcuts, and the app keeps running after its last window closes.
  - Windows: a menu bar in each window, Ctrl shortcuts, and the app quits with its last window. A PDF opened while PDFLion runs goes to the running process.
  - Linux: like Windows, but File > Quit with Ctrl+Q rather than Exit, GTK's About dialog, and GNOME's button order in the save prompt, with Save rightmost.

  Branch on `process.platform` in the module concerned. Before relying on an Electron API, check its `@platform` in `node_modules/electron/electron.d.ts`: many are macOS only, such as `isDocumentEdited()` and the `recentDocuments` role, and some leave out Linux, such as `app.addRecentDocument()`, `setAppUserModelId()`, `query-session-end` and the About panel's `credits`.
- Code is written on a Mac. Report anything Windows- or Linux-specific as unverified until it has run there.

## Stack

- Electron (latest stable), with the main process as ES modules. Plain JavaScript with JSDoc: no TypeScript, no bundler, no UI framework. The preloads are CommonJS, as sandboxed preloads must be. The web app is the same: ES modules for its shell and service worker, and classic scripts where they must run before pdf.js's or Home's.
- Two production dependencies, pinned to exact versions. When updating one, check what it brings along against its group in `credits.js` and README's Credits:
  - [@cantoo/pdf-lib](https://github.com/cantoo-scribe/pdf-lib), an MIT fork of pdf-lib, for the page changes pdf.js can't make. It parses documents, so it runs only in the sandboxed viewer: `bridge.js` loads its browser build from `/lib/`, which bundles its own dependencies.
  - [electron-updater](https://github.com/electron-userland/electron-builder/tree/master/packages/electron-updater), in main (see Updates). `npm ls --omit=dev --all` lists what it brings into `app.asar`.
- electron-builder: a `.dmg` and a `.zip` per Mac architecture (arm64, x64), an NSIS installer for Windows x64, and a `.deb` for Linux x64. No certificates and no notarization. Mac builds are signed ad hoc (see Packaging).
- Node 24 LTS (`.nvmrc`). The pdf.js build needs Node `>=22.22.3 || >=24.15.0 || >=26.0`.
- GitHub Actions (`.github/workflows/ci.yml`) tests on all three platforms, and builds and releases every push to `main`. A pull request into `main`, such as `dev`'s, and a push to `dev` run the tests only. Its `web` job builds and tests the web app on macOS, and its `pages` job deploys it to GitHub Pages after each release.

## Commands

```sh
git clone --recurse-submodules https://github.com/xLion-ch/PDFLion.git
npm install
npm run pdfjs:build      # build the pinned pdf.js viewer (once per clone and after each update)
npm start                # run in dev; npm start -- path/to/file.pdf opens a file
npm test                 # unit tests
npm run test:e2e         # end-to-end tests, in invisible windows that never take the focus (not on CI)
npm run test:web         # build the web app, and test it in Playwright's WebKit and Chromium
npm run web:build        # the web app into dist/web/; -- --version <v> for another version than CI's
npm run web:serve        # serve dist/web/ at http://localhost:8080/PDFLion/; -- --https for an iPad
npm run build            # tests, then every version this machine can build, in dist/
npm run dist             # this platform's installers in dist/; npm run dist -- --dir for the apps alone
node scripts/version.js  # the version CI builds this commit as
npm run web:trials       # build the iPad trials and serve them; -- --https for an iPad (see README)
node test/trials/run.js  # the trials that need no hands, in Playwright's WebKit and Chromium
```

## How the viewer is served

Everything a window loads comes from the privileged scheme `pdflion://app/` (standard, secure, fetch, stream):

| Path | Serves |
|---|---|
| `/viewer/…` | the pdf.js build. Into `web/viewer.html` the handler injects `overrides.css`, `geometry.js`, `texts.js` and `bridge.js`, and adds a CSP header |
| `/pdflion/…` | `src/viewer/` |
| `/tabs/…` | `src/tabs/`, with a CSP header of its own for `tabs.html` |
| `/home/…` | `src/home/`, with the same CSP header for `home.html` |
| `/shared/…` | `src/shared/`, for `texts.js`, which the viewer, the strip and Home load before their own scripts |
| `/lib/…` | @cantoo/pdf-lib's `dist/`, of which only `pdf-lib.min.js` is packaged |
| `/doc/<token>/<name>.pdf` | a file the user opened, or an untitled document, whole or as byte ranges. Main mints the tokens, so the renderer reads only what the user chose |
| `/thumb/<id>.png` | a recent document's thumbnail, as `image/png` with `nosniff` |

- A window is a `BrowserWindow` whose page is the tab strip. Each tab is a `WebContentsView` that loads `viewer/web/viewer.html?file=/doc/<token>/<name>.pdf`, or `home/home.html` for a home tab, below the strip, or over the whole window in full screen. Moving a tab to another window moves its view, unsaved changes included. Main keys documents, edited state and commands by tab, not by window.
- The document must be same-origin: the generic viewer rejects a `file=` from another origin.
- `bridge.js` is a classic script, so its `webviewerloaded` listener is in place before the viewer's modules initialise. It sets `defaultUrl` to `""`, so pdf.js's demo PDF never opens.
- `bridge.js` works out `/lib/` and `/doc/` from the viewer's own URL, `../../lib/` and `../../doc/`, so that it works below another path than the origin's root too. `overrides.css` names its icons from the root (`/pdflion/icons/`).
- pdf.js makes range requests only for http(s), so `bridge.js` opens `/doc/` through a `PDFDataRangeTransport`, with `If-Match`, so that a changed file gets 412.
- The handler resolves every path against its root, and answers 404 for anything that escapes it.
- An untitled document from File > New lives in main's memory until its first save. Save on it always means Save As (`runCommand()` sends `saveAs`, also for the save prompts' Save), which turns its token into a file token.

The web app (`scripts/build-web.js`) has the same layout below `/PDFLion/` in `dist/web/`, with `index.html`, `sw.js` and `manifest.webmanifest` at its root, and `web/` for `src/web/`'s other files. Since GitHub Pages sends no headers, the CSPs from `csp.js` go into `<meta>` tags, and `build-web.js` puts `/PDFLion` before the icons the stylesheets name from the root. Into the copy of `viewer.html` it injects the CSP, `overrides.css`, `geometry.js`, `keys.js`, `viewer-host.js`, `texts.js` and `bridge.js`, and into `home.html` the CSP, `keys.js` and `home-host.js`. The service worker serves `doc/<id>/<name>` from the library, with the same contract as `/doc/`: byte ranges, an ETag of `"<id>-<revision>"`, and 412 for a stale `If-Match`, so the range transport works unchanged. Its body is a stream that reads the Blob 1 MiB at a time, since WebKit fails a response of a large Blob.

The service worker also keeps the app for offline use. `build-web.js` writes into `sw.js` the version, every other file of the build with its SHA-256 and size, and an id of those (`fileList()`, `buildId()`), so every build's `sw.js` differs, which is how browsers find an update. Installing fills the cache `pdflion-<version>-<build>`: a file an older version's complete cache has with the same contents is copied from there (`planInstall()` in `precache.js`), and the rest is fetched with `cache: "no-cache"`, past GitHub Pages' 10 minutes of HTTP caching, and checked against its size and SHA-256. The list of files goes into the cache last (`.pdflion-files.json`), so only a complete cache has one, and any failure fails the install, which the next check tries again. On a first visit, the shell then says the app couldn't be downloaded (`webAppNotDownloaded()`). So it does if `register()` hasn't settled after 15 s twice: the first time, it reloads (`registered()`), since WebKit on CI has left it unsettled. Once active, it serves the app's files only from its own cache, whatever their query (`fileAt()`), the folder itself as `index.html`, so a running app never mixes versions, deletes the other versions' caches, and takes over the pages. Anything that isn't the app's or the library's goes to the network.

## Home

Home lists the recent documents, newest first, with their first pages, and has Open… and New. It's a tab of a kind of its own (`kind: "home"` in `tabs.js`): no token, never edited, its own preload, and titled Home in the title of its tab and PDFLion in the title bar.

- Every window has one home tab from the start (`createWindow()` calls `openHomeTab()`), pinned as its leftmost tab in `tablist.js`: no tab goes before it, it doesn't move to another window or tear off, and the strip shows it as an icon alone, narrower than a document's tab, without a close button, not draggable. So the strip always shows, also with one document. In the web app, `shell.js` adds it at launch, and loads its frame once it's shown.
- Home closes only with its window. Close Tab on it closes the window (`closeTab()` in `unsaved.js`), the strip's close messages for it are ignored, and its context menu has only Close Other Tabs, which closes the documents. Closing a window's last document shows Home, and the window stays. A window left with only Home after its last document moved to another window, by a drop or Merge All Windows, closes (`afterTabLeft()`). Move Tab to New Window and tearing off need another document in the window.
- It shows at a launch without documents, or whose files all failed to open, on the Dock icon with no window open, for a second instance without files, and with File > Home (⇧⌘H, Ctrl+Shift+H). The viewer's toolbar has no Home button, since the strip always shows Home. `showHome()` selects the window's home tab.
- A document opens in a new tab at the end of the window (`openTab()`): from a card, Open…, New, a drop, Finder or a second instance alike. In the web app, after the active document, or at the end from Home. A card whose document is open shows its tab instead.
- PDFLion keeps its own recent list on every platform (`recent.js`, `recentlist.js`), 30 for Home and 10 for Open Recent on Windows and Linux, in `state.json` under `recent`. It still feeds macOS's list and the Windows jump list. Each entry has a random id, which is all the page knows: it never sends a path.
- Thumbnails: `bridge.js` renders page 1 to fit 180 × 240 CSS pixels at the screen's pixel ratio, once the viewer has shown a page and after each save, and sends it as a PNG (`setThumbnail()`). Main keeps it only for a document on the list, and only a PNG of at most 512 × 512 pixels and 256 KiB by its header (`isThumbnail()`), without decoding it. Only Home's sandboxed page decodes it.
- The context menu (Open, Show in Finder, Explorer or Files, Remove from Recent) is main's, also after a long press (see Pens and touch). Delete or Backspace removes the focused card, and a document whose file is gone shows as missing, and offers to come off the list.
- `home.css` repeats the viewer's colour roles, as `tabs.css` does. Its title has the app's logo, `logo.svg`, a copy of `resources/icon.svg` to keep in step with it. `home.html`'s texts name their ids in `data-text` and `data-label`, which `home.js` fills in from `texts.js`.

## Page changes

pdf.js's page tools are on (`enableSplitMerge`, `enableMerge`): in the sidebar's thumbnails, checked pages can be dragged, copied, cut, deleted and exported, and Add file or dropped files add pages. `bridge.js` fits them into PDFLion's saving and edited state:

- Moves, copies and deletions stay in pdf.js's `pagesMapper` until Save, which writes the file `extractPages()` makes of them, with typed form values (`currentBytes()`), then `reopen()`s it. They count as edits while the pages' order differs from the document's (`hasPageChanges()`), since pdf.js's `hasStructuralChanges()` stays true after an Undo.
- `bridge.js` replaces `onSaveAndLoad()` before pdf.js binds it, so that Add file works like Insert Blank Page: one change at a time, the locks and the signing prompt first, form values kept, and the document as it was if the result doesn't open. `preload.cjs` lets PDFs dropped on the thumbnails through to pdf.js while `#thumbnailsView` has `isDraggingFile`. Dropped anywhere else, they open as tabs.
- An undone deletion leaves the wrong page in pdf.js's page cache, which printing and Find use, so `recachePages()` caches the pages again after every page edit.
- Insert Blank Page and the overview's Rotate Pages go through @cantoo/pdf-lib, as incremental updates appended to `currentBytes()` (`forIncrementalUpdate`, `updateMetadata: false`), so the original bytes, metadata, page labels and signed revisions stay as they were. `reopen()` shows the result in the same tab, with its view, sidebar and overview, and `viewOnLoad` set to `INITIAL`, since the fingerprint stays the same. If the library or pdf.js fails, the tab gets its bytes back, with an alert. One busy flag covers Save and every page change.
- Documents with a password, even an owner password only, and pure XFA forms are locked against page changes, since the library's increments to encrypted files aren't reliable. `guardPageTools()` captures the page tools' events before pdf.js's listeners, and `pdflionPagesLocked` on `#outerContainer` hides the tools. A signed document asks once per tab before its first change (`confirmPageChange()`). A drag can't be replayed, so it asks once the press has moved far enough to start one.
- A save that writes a new file through `extractPages()` first asks whether to drop what the document holds and the new file won't (`confirmRewrite()`, with what `findDroppable()` found), once per item and tab. An insertion or rotation after unsaved page changes starts from the new file `currentBytes()` writes, which `newFile` tracks until the next save.
- Every word of the page dialogs is in `src/shared/wording.js`, which the page asks for by reason through `pdflion:page-dialog`, and `pages.js` shows.

The page overview (View > Page Overview) is pdf.js's views manager on its thumbnails, made a grid by `overrides.css` while `#outerContainer` has `pdflionPageOverview`. Its header gets Rotate Pages Left and Right, and Insert Blank Page, before Add file, and so does the sidebar's while it shows the thumbnails: `overrides.css` shows them wherever pdf.js shows Add file. They act on the checked pages, Insert Blank Page after the last one, and else on the current page.

- The document stays where it was, behind it: `bridge.js` keeps the views manager's `onResizing()` from moving it aside.
- pdf.js places the thumbnails for dragging on a `resize` from the views manager, so `bridge.js` sends one whenever the grid moves: as it opens and closes, as the window resizes, and on `reopen()`.
- pdf.js shows its sidebar button on while the views manager is open, so `showSidebarButton()` shows it off while the overview is. Toggling the sidebar closes the overview: `bridge.js` wraps the views manager's `toggle()`, which F4 and the menu call, and a capture listener takes the button's clicks.
- A click on a page opens it: pdf.js goes to it, and a capture listener on `#thumbnailsView` closes the overview a task later. pdf.js stops the click that ends a drag of pages before it gets there.
- View > Rotate Left and Right turn only the view, which isn't saved.

## Eraser

A drawing tool of PDFLion's after Pencil, `#pdflionEditorEraserButton`, with an option box. `bridge.js` builds it, `geometry.js` works out what it touches, and `overrides.css` styles it.

- It works in pdf.js's ink mode, where the file's ink annotations are editors too. Turning it on commits Pencil's open drawing session (`unselectAll()`, twice). pdf.js then shows Pencil on, which `overrides.css` shows off under `pdflionErasing`. Pencil's click would turn ink mode off, so a capture listener makes it just stop erasing.
- A capture listener on `#viewerContainer` takes presses on pages before pdf.js, and the drag's moves are captured on window.
- It takes Pencil's drawings (`editorType` `"ink"`) and highlights, but not signatures, which are drawings too. Highlights serialize to nothing until saved, so `highlightOf()` reads their place from pdf.js's outlines: a free highlight's line, and a text highlight's boxes. Object mode removes whole drawings. Line mode cuts strokes, and once per frame replaces each cut drawing with one for each stroke left of it, built through the layer's `deserialize()`, so each piece is a drawing of its own. It takes highlights whole in either mode. `addWithoutUndo()` masks the step to undo pdf.js's `onceAdded()` would add for each.
- A drag is one step to undo (`addCommands()` with `mustExec: false`). pdf.js builds editors asynchronously, so all the eraser's work runs in one queue (`afterErasing()`).
- A pen's eraser end (`button` 5) erases with any tool on, which stays on (`inPlace`). With no tool on, it turns the eraser on, and erases once `annotationeditormodechanged` says ink mode is on. The eraser then stays on, since with no tool on pdf.js takes no Undo, and its disabled layers wouldn't show an undone erase.
- While only a pen draws, fingers don't erase, and the pages keep their `touch-action`, so fingers scroll. A pen hovering over a page moves the circle.
- Its mode and size are tool settings, the same in every tab (`toolsettings.js`). The circle cursor is a `div`, since a CSS cursor can't grow that large.

## Favourites

A favourite is a drawing tool with its settings, such as a blue pencil 1 pt wide, or the eraser with its mode and size. Main keeps them in `state.json`, and sends every tab the whole list after each change. Save as Favourite goes at the end of the option boxes of Highlight, Text, Pencil and the Eraser. The favourites show before pdf.js's drawing tools (`#pdflionFavourites`), and those that don't fit in the ★ menu.

- Settings are read from the option box's inputs, which pdf.js keeps in step with the tool or the selected drawing. Highlight's colour is the swatch marked `aria-selected`, by its upper-case `data-color`. Where the colour input takes an alpha channel, Pencil's opacity is in the colour, since pdf.js then removes the slider, in the browser's own format: `#rrggbbaa`, or Safari's and Firefox's `color(srgb r g b / a)`, which `colorValues()` reads as pdf.js's `getRGBA()` does.
- A click (`useFavourite()`) first commits Pencil's drawing and clears the selection (`commitDrawing()`), since pdf.js gives new settings to selected and open drawings. Then it switches the tool, and dispatches `switchannotationeditorparams` for each setting, and `annotationeditorparamschanged`, since pdf.js doesn't update its option boxes for these.
- A click on the favourite that's on, its tool on with its settings, turns the tool off instead (`isFavouriteOn()`).
- The Eraser's favourite has no colour. Using it makes its mode and size the eraser's, in every tab, and turns the eraser on (`useEraserFavourite()`).
- The tool's option box stays closed. pdf.js opens it as it switches tools, and calls external listeners after its own, so `followFavourites()` closes it again on `annotationeditormodechanged`.
- Which favourite shows pressed is read a microtask after pdf.js's events, since Highlight's colour picker marks its swatch only after dispatching.
- Reordering with a mouse is HTML5 drag and drop with a data type of its own (`FAVOURITE_DRAG_TYPE`), which the preload and the strip leave alone. A drop rebuilds the buttons, so it ends the drag itself. A finger or a pen drags with Pointer Events instead (`dragFavourite()`), once its long press has opened the menu, which moving on closes, as iPadOS's context menus do. Meanwhile the button isn't `draggable`, so iPadOS starts no drag of its own, and touchmoves are cancelled.
- The ★ menu copies pdf.js's Stamp menu, and repeats `web/menu.js`'s keyboard handling, which `bridge.js` can't import. Remove Favourite is main's context menu, which a long press opens too (`addLongPress()`), after which a drag closes the host's menu (`closeMenu`, the web app's).

## Pens and touch

For the Apple Pencil in the web app, and pens and touchscreens on the desktop, such as a Surface's. `bridge.js` does it all without pdf.js patches, `followPen()` most of it.

- **Pen-only drawing** (`penOnly` in `tools.js`), as iPadOS's Only Draw with Apple Pencil: the first pen to press on a page turns it on, unless it was ever turned on or off (`penOnlyChosen`, which main and the shell set with any change to `penOnly`, through `changeToolSettings()`, and the viewer can't send). Its item at the top of the ⋮ menu (`addPenOnlyItem()`) turns it on and off, and so does the web app's ⓘ menu. It applies to every tool, so no tool's option box has it, where it looked like that tool's own.
- While it's on and Pencil, Highlight or the Eraser is on, a capture listener on `#viewerContainer` keeps a finger's presses on pages from pdf.js's layers, with `stopPropagation()` but no `preventDefault()`, so the browser scrolls and pdf.js's `TouchManager` pinches. `pdflionPenOnly` on `#outerContainer` lifts the `touch-action: none` of the Eraser's pages, Highlight's text layer and text boxes.
- **Resting palms:** while a pen is down on a page with one of those tools on, or its eraser end with any, every touchmove is cancelled where it still can be, and no touchstart reaches pdf.js's pinching, which would end the stroke. Nor does a pen's own touch while those tools are on, by Safari's `touchType` `stylus`.
- **Long presses** of 500 ms, moving at most 10 px, with a finger or a pen, dispatch a `contextmenu` event where they are, which iPadOS doesn't, so the existing menus show: a favourite's (`addLongPress()`), a tab's (`tabs.js`) and a card's (`home.js`), the same code three times. Chromium's own long press, and the click after one, are dropped.
- **Lost lifts:** a press that ended badly mustn't stop the next (`followLostLifts()`). A pen's next press, or any press outside the pages, first gives pdf.js the lift it never got, since it would wait for that pointer and draw nothing, and a stroke left open across tools would end as the new tool's. A layer's `#hadPointerDown` is forgotten after every lift and cancel, through its `pointerdown()` with no target, or the next press is ignored.
- **No zooming the app:** the toolbar, the strip, dialogs, menus and Home get `touch-action: manipulation`, no callout and no text selection but in fields. The web app's shell and hosts prevent `gesturestart` outside `#viewerContainer`, since Safari ignores `maximum-scale`.
- **A trackpad's pinch:** Safari sends it as gesture events alone, where Chromium sends wheel events with `ctrlKey`, which pdf.js zooms by. So on the pages `followTrackpadPinch()` prevents them and zooms with `updateZoom()`, from the scale the pinch started at, unless a finger is on the screen, whose pinch is `TouchManager`'s, or wheel events with `ctrlKey` come along.
- **Turning pages:** in Page Scrolling (`ScrollMode.PAGE`), a click or tap on the viewer's background beside the page goes to the previous or next page, and so does a finger's swipe across, at least 50 px within 800 ms (`followPageTurns()`). The swipe follows Touch Events, which go on while Safari pans, and leaves out the Pencil's own touches, a drawing tool fingers draw with, the eraser, and a page wider than the view.
- **Touch targets:** with `(pointer: coarse)`, the toolbar's buttons stay 40 px at every step, and menu items and the eraser's modes are 44 px high. In the web app the strip's tabs and close buttons, Home's buttons, and the dialogs' and menus' items are 44 px too.

## The zoom button

pdf.js's zoom select, `#scaleSelect`, is hidden, and `#pdflionZoom` stands in its place (`addZoomMenu()`): a narrow button that shows a named zoom's icon, such as Page Width's, or else the percentage, with a menu like the ★ menu's of the select's choices, in pdf.js's words, the named ones with their icons. Choosing one picks it in the select, whose `change` pdf.js follows, and `followZoomMenu()` follows `scalechanging`.

## The toolbar's width

Print, and the web app's Share, are always in the ⋮ menu, as pdf.js has them in its medium view: `overrides.css` hides their group in the toolbar.

The toolbar's width depends on the language, the page count, the favourites and a signed document's button. So `layoutToolbar()` gives up as little as it can as a window narrows, one step at a time, each keeping those before it (classes of `#toolbarContainer`, `TOOLBAR_STEPS`): 32 px buttons, favourites into the ★ menu from the last, pdf.js's medium view (every favourite into ★), pdf.js's small view (no previous and next page buttons), no zoom button, and the drawing tools in one button showing the one that's on, with a menu of them (`addToolsMenu()`). Narrower than a desktop window gets, Find, Page Overview and Insert Blank Page go into the ⋮ menu (`addNarrowMenuItems()`), then the zoom buttons and the status go, and last Undo and Redo go into the tools' menu.

- At the tools' step their buttons are hidden and their places shrink to nothing at its right, where their option boxes still open. A signed document's button stays.

- It never takes fewer steps than pdf.js's own media queries at that width (`PDFJS_STEPS`: 750, 690 and 560 px), and as the window narrows, the toolbar only ever loses more. `overrides.css` repeats pdf.js's rules for those views under the classes, in `:where()`.
- A `ResizeObserver` lays it out again, on everything but the right group, which the favourites change.
- A window's content is at least 560 px wide (`MIN_WIDTH` in `windows.js`), where the toolbar fits after its fifth step in English and German for 1000 pages. `toolbar.spec.js` checks it. The web app's toolbar fits down to 320 px, an iPad's in Slide Over, where `overrides.css` lowers pdf.js's minimum of 350, with favourites and a tool on too, which `test/web/layout.spec.js` checks.

## Menu commands

- Items that act on the document come from `commandItem()` in `menu.js`, and are enabled only while the focused window's active tab is a document, not Home. A click calls `runCommand(tab, command)` (`ipc.js`), which sends the command to the tab's `bridge.js`, where `COMMANDS` maps it to pdf.js. A new command needs all three, and an end-to-end test.
- Items that act on tabs come from `tabItem()`, and run in main: in the Window menu on macOS, at the end of View on Windows and Linux.
- PDFLion's own shortcuts follow Preview: Page Overview ⌥⌘6, its Contact Sheet, Insert Blank Page ⇧⌘N and Eraser ⇧⌘E, and Home ⇧⌘H. On Windows and Linux they're Ctrl+Shift+O, since Ctrl+Alt+6 is AltGr+6, Ctrl+Shift+N, Ctrl+Shift+E and Ctrl+Shift+H.
- The page sees keys before the native menu. `isMenuShortcut` in `bridge.js` keeps pdf.js from acting on the shortcuts it shares with the menu, so a new shortcut that pdf.js also binds needs adding there. It takes ⌘ or Ctrl as the preload's `commandKey` says (`meta` on macOS), and F4 with Ctrl. pdf.js binds none of the tab shortcuts, nor PDFLion's own above.
- Edit > Undo and Redo aren't roles, whose undo reaches editable text only. `undoItem()` asks `bridge.js` first, which dispatches pdf.js's `editingaction` while a drawing tool is on and no text is being typed. Otherwise main calls `webContents.undo()` or `redo()`.
- pdf.js's storage counts an annotation joining it as a change, but not a change to one in it, and Pencil's strokes join it only once its drawing ends. So `followEditorChanges()` counts every command, undo and redo of the editors' UI manager as a change, Pencil's strokes too, and Save ends Pencil's open drawing first, so that they're saved: `endPencilDrawing()` calls each layer's `commitOrRemove()`, which unselects nothing, as `unselectAll()` would.
- Each of Pencil's strokes is a drawing of its own: `followPencilStrokes()` ends Pencil's drawing a task after each `pointerup`, after pdf.js has ended the stroke, unless another has started, and unselects it. So the eraser's Object mode, Undo and Redo take a stroke at a time. While Pencil is on, `overrides.css` shows its drawings without their box, handles and toolbar, and lets presses through them to the layer, so that a stroke started over another draws rather than moving it.
- A click on the native menu gives the page no user activation, so `runCommand()` grants it for `COMMANDS_NEEDING_ACTIVATION`, such as Presentation Mode's `requestFullscreen()`.
- Labels mark access keys with `&`, as in `&File`, which macOS drops. A literal `&` is `&&`.
- File > Export Settings… and Import Settings… (`settingsfile.js`) work without a window, like New. A settings file (`backup.js`) holds the eraser's settings, pen-only drawing, the favourites and automatic updates. Importing asks first, replaces the settings the file has, and adds its favourites that aren't there yet (`addFavourites()`).

## Updates

The packaged app updates from the GitHub releases, through electron-updater (`updates.js`), which `app-update.yml` in the app's resources points at.

- It checks 10 s after launch and every 6 hours while automatic checks are on (`updates.automatic` in `state.json`), downloads in the background, checks the SHA-512 against the release's `latest*.yml`, and takes neither downgrades nor prereleases.
- `updates.js` makes `MacUpdater`, `NsisUpdater` or `DebUpdater` itself, since electron-updater's `autoUpdater` picks the Linux one by a file only the `.deb` has. It `import()`s electron-updater, a CommonJS module, when the first check is due.
- Restart Now first asks about every edited tab (`reviewUnsavedChanges()` in `unsaved.js`), then calls `quitAndInstall(true, true)`, which can't be taken back. Meanwhile Windows and Linux don't quit with their last window (`isRestartingForUpdate()`).
- macOS: Squirrel.Mac installs the zip, on quit or with Restart Now, if the new bundle satisfies the running one's designated requirement (see Packaging). `MacUpdater` serves it the zip from a proxy on 127.0.0.1, and the prompt waits for Squirrel's own `update-downloaded`, about a second after electron-updater's. An app on a read-only volume can't update, such as one run from the DMG, or from Downloads, which macOS translocates. A check from the menu then says to move it to Applications.
- Windows: the NSIS installer installs silently for the user, on quit or with Restart Now. Once Windows asks to end the session, quitting installs nothing, in case Windows ends the installer halfway. Whether that's needed hasn't been tried.
- Linux: `dpkg -i` through `pkexec`, which asks for a password, so only Restart Now installs. A failure, such as a cancelled prompt, shows as an error during `quitAndInstall()`, and PDFLion says the update wasn't installed.
- electron-updater's staging ID (`x-user-staging-id`) goes out empty, so GitHub can't follow a copy from one IP address to the next.
- The dev app gets no updates, except from an end-to-end test's local feed (`--pdflion-update-config=<app-update.yml>`, which sets `forceDevUpdateConfig`). The packaged app ignores the switch.

## The web app

The web app runs PDFLion where Electron can't, first in Safari on an iPad, from the same parts: pdf.js's build with `bridge.js`, `geometry.js` and `overrides.css`, Home, and the tab strip. Its shell (`index.html`, `shell.js`) does what main does: it keeps the tabs (`tablist.js`, with one window), shows each in a frame, the viewer's or Home's, routes commands, shows dialogs (`dialogs.js`), and keeps the library and the tool settings.

- Each frame's host makes a `MessageChannel` and posts a port to the shell, which takes it only from one of its own frames, with the page of the tab's kind. Requests carry an id for their reply, in the shape of `ipc.js`'s channels, and the shell checks every payload as main does, with `tools.js`, `thumbnail.js` and `isPageDialog()`. pdf.js dispatches `webviewerloaded` at the shell's document, so `bridge.js` listens there too, for its own window.
- The strip is `src/tabs/tabs.js`, with `window.pdflionTabs` from the shell, Home always its leftmost tab. With one window, tabs don't go to another. Inactive frames are hidden and `inert`. A tab that's left saves its document (`saveNow`), and closing the last document shows Home.
- **Sleeping tabs:** iPadOS limits a web app's memory, and each frame runs its own pdf.js, so at most 4 documents keep their frames (`MAX_LOADED_DOCUMENTS`), a guess until it's tried on an iPad. Beyond that, the one shown longest ago (`shownAt`) saves and loses its frame (`sleepTabs()`), unless its changes couldn't be saved, and loads again where it was once it's shown, without its undo history. Home never sleeps.
- **The session:** the shell keeps the open tabs, Home first, their order, the active one, and where each document was in the library's `session` store (`session.js`), at once after each change, a view's 1 s after, and when the page is hidden, since iPadOS ends suspended web apps without warning. `bridge.js` tells a host with `setView` the page, zoom and top left of pdf.js's location, at most every 500 ms (`followView()`), and the viewer's URL takes it back as its hash (`viewHash()`), which pdf.js shows the document at. A launch restores the tabs, documents deleted meanwhile left out, with only the active one loaded, or shows Home without any.
- The library (`library.js`) is IndexedDB database `pdflion`: `documents`, a record each (name, size, dates, `revision`, `exportedRevision`, `source`, `sha256`), `bytes`, `thumbnails`, `settings`, and `session`. A save writes the bytes and raises the revision in one transaction. A file whose SHA-256 the library has opens that document. New makes `Untitled.pdf` there at once, which goes again if it's closed unchanged. `upgrade()` takes a database of any earlier version along.
- Autosave is `bridge.js`'s, for a host with `autosave`. Form values, annotations, and inserted or rotated pages save 2 s after the last change, 1 s more for each 10 MB up to 30 s, and never mid-stroke. Changes with pdf.js's page tools wait 30 s, and not while its undo bar shows, since saving them reopens the document. Everything saves at once when the page is hidden, before a tab closes or is left, and for ⌘S (`saveNow`). A change with the page tools whose new file would drop what the document holds asks before the change rather than at the save (`confirmPageChange()` with a `Rewrite`). A failed save says so once, and stays edited for the next try.
- The library's copy is "not in Files" while its `revision` is higher than its `exportedRevision`, which an import sets, and a completed Share. A new document's is -1: "Only in PDFLion". The first save ever explains it in a dialog, each document's first save in a session in a snackbar, with Share…, and so do the toolbar's status (`onSaveStatus`), Home's mark, and a snackbar after the tab closes. `wording.js` words all of it.
- Share (`share`) saves first, then the shell shares the stored revision with `navigator.share()`, or the tab's bytes if they couldn't be stored. If the save used up the tap's activation, it asks for another tap. Where files can't be shared, it downloads the file. Any completed share counts as exported.
- Without a native menu (`nativeMenu: false`), pdf.js keeps ⌘P, ⌘F and the zoom keys, and the toolbar gets Undo and Redo while a drawing tool is on. `keys.js` has PDFLion's shortcuts, as the desktop's menu has them, which the hosts take before pdf.js and hand to the shell. ⌘O, and Open… in Home and the ⋮ menu, open a file picker in the frame where they happen, since iPadOS opens one only in response to the user.
- Home is the same page, through `home-host.js`: the library's documents with their sizes, and an ⓘ menu (About, Check for Updates…, Export…, Import…, Draw Only with a Pen, the storage used) instead of Clear. Its context menu has Open, Share…, Rename… and Delete…, which asks first, and Delete or Backspace on a card deletes too.
- **Updates** (`updates.js`): the shell calls `registration.update()` at launch, on the `online` event, when the app shows after at least 15 minutes hidden, and every 6 hours, only while `navigator.onLine`, and says nothing when a check fails. A new version downloads what changed and waits. Once it has installed, the shell asks it for its version and offers it (`webUpdateReady()`), with Release Notes, which opens `releases/tag/v<version>` and asks again, Later and Restart Now. Restart Now saves every document and the session, asks about changes that couldn't be saved (`restartUnsavedPrompt()`), then sends the worker `skipWaiting`, and reloads on `controllerchange`, after which the session brings the tabs back. Any other `controllerchange`, from another of the app's pages, saves and reloads too. Later leaves it until nothing runs the old version, and the next launch offers it if it still waits, as Check for Updates… does at any time, which also says when the app is up to date or the check failed.
- **Export and import** (`src/web/backup.js`): Export… asks for Settings Only, a settings file as the desktop's (`platform` `web`, no automatic updates), or Settings and Documents, a backup: `PDFLion Backup <date>.zip`, stored (`zip.js`), of `PDFLion Settings.json`, `Library.json` (`writeLibraryFile()`), every document's latest revision as `Documents/<name>`, with " 2" for repeats (`documentFiles()`), and `Thumbnails/<id>.png`. It saves every tab first, shows its progress with Cancel while it works out the CRC-32s, and hands the file to the shell's Share, which downloads it where files can't be shared. The ZIP is a Blob of the library's Blobs, never in memory. A backup changes no "not in Files" mark.
- Import…, a file picker in the shell, and a backup or settings file dropped on Home take either, by whether it starts with `PK`. A backup's `Library.json` and settings may be in a folder, as after Finder's Compress, and `__MACOSX/` is left alone. A document whose id, revision and size are here is skipped, one whose id is here otherwise comes in as a copy with a new id and the next free name, and every document keeps its record, so its "not in Files" mark comes back. It asks first, with what it will do (`importBackupPrompt()`), and checks `navigator.storage.estimate()` against the sizes before it stores anything. Each document goes in a transaction of its own (`importDocument()`, which adds and never replaces), once its size and CRC-32 are checked and it starts as a PDF, with its thumbnail if `isThumbnail()` takes it. Those that fail are named at the end, and the rest stay. Settings replace the eraser and pen settings where they differ, and add the favourites that aren't here yet.
- **The title bar:** in a Home Screen app on iPadOS (`navigator.standalone`), the shell leaves a narrow band of the strip's colour above the strip (`homeScreenApp` in `web.css`), where iPadOS 26 blurs and fades the window's top edge, and starts the tabs right of the window's controls, which iPadOS draws at the top left. The safe area covers neither.
- **The Home Screen icon:** iPadOS takes it from the `apple-touch-icon` link as the app is added, and keeps it, so `shell.js` points the link at the dark icon while the appearance is dark.
- **Hosting:** GitHub Pages serves `dist/web/` at `https://xlion-ch.github.io/PDFLion/`, deployed by CI after each release (see Packaging). Pages sends `Cache-Control: max-age=600`, which the service worker's downloads bypass.

## Security rules

- Every window and tab view uses `contextIsolation: true`, `sandbox: true` and `nodeIntegration: false`, and `app.enableSandbox()` sandboxes every renderer.
- The preloads expose small APIs through `contextBridge`, never `ipcRenderer`: `window.pdflion` only on the viewer page, `window.pdflionTabs` only on the tab strip, and `window.pdflionHome` only on Home, since a preload runs in every page its `webContents` shows.
- Main validates the sender and the payload of every IPC message. The sender must be the top frame, with the viewer's URL (`ipc.js`), for the strip's channels the strip's (`strip.js`), or for `pdflion-home:*` Home's, in a home tab (`home.js`). Home names documents only by ids of the recent list. A strip message must also come from a window's own `webContents`, with tab ids of that window and indexes in range. Don't compare origins instead, as Electron's checklist suggests: an `about:blank` page the viewer opens has its origin, and the strip shares it too.
- The tool settings' channels (`toolsettings.js`) take only what `tools.js` accepts, rebuilt from known fields, so nothing else reaches `state.json`. `pdflion:page-dialog` takes only a reason and items from `wording.js`'s fixed lists (`isPageDialog()`).
- Tab ids are random and unrelated to document tokens, since drags carry them out of the app. Main takes a dropped tab only after a strip reported dragging it.
- Tabs can't navigate away from `pdflion://app/viewer/`, home tabs not from Home, and the strip can't navigate at all. Only `http`, `https` and `mailto` links open, with `shell.openExternal`, and every other `window.open` is denied.
- `viewer.html` gets a CSP without `unsafe-eval`, with `wasm-unsafe-eval` for pdf.js's image decoders. `tabs.html` and `home.html` get only their own scripts, styles and images.
- `pdflion:thumbnail` takes only a PNG of at most 512 × 512 pixels and 256 KiB, by its header, from a document with a file on the recent list, and main never decodes it.
- Import Settings… reads at most 1 MiB of the chosen file, and only a settings file, never a ZIP. `readSettingsFile()` rebuilds every part through `tools.js`'s checks and drops the rest, so nothing else reaches `state.json`.
- The web app's Import… treats a backup as untrusted. `zip.js` checks every record's offsets and sizes against the file, refuses entries that overlap or lie outside it, reads a central directory of at most 64 MiB and 100,000 entries, stops inflating at an entry's stated size, and checks each entry's CRC-32. `readLibraryFile()` rebuilds every record from known fields, with UUIDs, file names and paths in their folders, and the shell stores a document only once its size matches its record and it starts as a PDF, which pdf.js then opens as any other.
- @cantoo/pdf-lib parses untrusted documents, so it runs only in the sandboxed viewer, never in main.
- Permissions are denied, except `fullscreen` and `clipboard-sanitized-write` for the viewer (`permissions.js`).
- The updater's requests to GitHub, over HTTPS, are PDFLion's only network requests of its own. Releases aren't signed, and only the SHA-512 in the same release checks a download: `NsisUpdater` checks no Authenticode signature without a `publisherName`, and Squirrel's check of the designated requirement proves nothing, since any app can claim the bundle ID. So whoever can publish a release can run code on every installed copy, and the workflow's permissions and the ruleset on `main` guard that. Release text is never shown.
- CI has a read-only token (`contents: read`), runs pull requests on `pull_request`, never `pull_request_target`, checks out with `persist-credentials: false`, uses only GitHub's own actions, pinned to commits, and installs with `npm ci`. Only the `release` job gets `contents: write`. It runs no code from the repository, and only for pushes to `main` in `xLion-ch/PDFLion`, in the `release` environment, which allows only `main`. Only the `pages` job gets `pages: write` and `id-token: write`, on the same terms, in the `github-pages` environment, which allows only `main`, and it checks nothing out: it deploys the `web` job's build with `actions/deploy-pages`.
- The packaged app's Electron fuses turn off `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS`, `--inspect` and file:// privileges, load the app only from `app.asar`, checking its hash on macOS and Windows, and encrypt cookies.
- The web app's pages get their CSPs from `csp.js` as `<meta>` tags, none with `unsafe-eval` or `unsafe-inline`. The shell's allows frames, its manifest and its service worker from its own origin only, and Home's `blob:` images for the thumbnails.
- The web app has no process isolation: the shell, Home and every viewer frame share one origin, so a pdf.js exploit could read the whole library, where on the desktop a renderer reads only its own token's file. The defences are the CSP without `unsafe-eval`, which stopped CVE-2024-4367, and pdf.js's sandbox for PDF scripts.
- A `<meta>` CSP can't set `frame-ancestors`, so the shell runs only as the page itself, and the hosts only in a frame of the shell, at the app's folder on its origin. Elsewhere they stop the page and go to `about:blank`.
- `viewer-host.js` lets links and `window.open` open only `http`, `https` and `mailto` URLs, and places in the viewer itself.
- The web app's only requests are for its own files, on its own origin. Its service worker checks each file against the SHA-256 its `sw.js` lists, which keeps a version whole, but proves no more than that `sw.js` came from the same place: whoever can deploy to the site runs code in every installed copy at its next check, as on the desktop. Any other GitHub Pages site of the xLion-ch account shares that origin, and could read the library, so the account keeps none with third-party scripts.

Against Electron's [security checklist](https://www.electronjs.org/docs/latest/tutorial/security) (reviewed for Electron 45), the rules above meet every item that applies. Beyond them: no device or screen-sharing permission handlers are set, so those APIs fail; no window enables `webviewTag`; `about:blank` and `about:srcdoc` pages, which `will-navigate` doesn't see, get no preload API, and main ignores their messages; `LoadBrowserProcessSpecificV8Snapshot` stays off, since there's no browser-only snapshot; and on Linux nothing checks `app.asar`'s hash. Downloads keep Electron's save dialog, for attachments, a script's Save As and Export selected.

## Packaging

- Mac builds are signed ad hoc (`identity: "-"`): Apple silicon runs only signed code, and the fuses change the Electron binary, so an unsigned build is killed at launch.
- An ad-hoc signature's designated requirement is the app's own hash, so Squirrel.Mac would refuse every update. `scripts/after-sign.js`, electron-builder's `afterSign` hook, signs the bundle alone again, ad hoc, with `designated => identifier "io.github.xlion-ch.pdflion"`, keeping its identifier, entitlements and hardened runtime, then verifies it. `mac.requirements` can't do that, since it gives every nested binary the requirement, which they then fail. electron-builder warns that it skips the hook on Windows and Linux.
- `fileAssociations` has `rank: Alternate`, so PDFLion is in Open With without becoming the default. The NSIS installer is one-click and per user, into `%LOCALAPPDATA%\Programs`.
- Of @cantoo/pdf-lib, `app.asar` holds only `dist/pdf-lib.min.js`, its licence and its `package.json`: the `files` patterns leave out about 30 MB.
- electron-builder's `makensis` is an Intel binary, so the Windows installer needs Rosetta on Apple silicon.
- `publish` names the GitHub releases, so every build writes `latest-mac.yml`, `latest.yml` or `latest-linux.yml`, a `.blockmap` for each but the `.deb`, `app-update.yml` into the resources, and `resources/package-type` into the `.deb`. On macOS only the zip and DMG targets get `app-update.yml`, not `--dir`. A build that fails on any target writes no `.yml` at all.
- CI's version comes from `scripts/version.js`: `package.json`'s major and minor, and the commit count, so the same commit always gets the same version, and each push a higher one, without CI committing. `-c.extraMetadata.version` puts the version everywhere. `version.js` refuses a shallow history. `package.json` keeps `x.y.0`, and raising major or minor is a hand edit there.
- Only a push to `main` builds the installers, which the run keeps for 14 days. Pull requests and pushes to `dev` build none, so the checks by hand before merging use installers built locally. The `web` job builds the web app as `scripts/version.js`'s version every time: for a push to `main` it uploads it for Pages (`actions/upload-pages-artifact`), and for a pull request from this repository, not a fork, as `PDFLion-<version>-web`, kept 14 days, to serve to an iPad before merging.
- Once all three platforms and the web app pass on a push to `main`, the `release` job makes `v<version>` with `gh`: it checks that every file is there, deletes any draft a failed run left, creates a draft on the commit with every file and generated notes, then publishes it as the latest release, which creates the tag. It releases nothing if the latest release has the same version or a higher one. Releases keep their `.blockmap` files for differential downloads. Only once it has published does it set its output `published`, after which the `pages` job deploys the run's web app, so a re-run or an older commit's run never deploys an older web app over a newer one. Re-running a failed `pages` job deploys that release's.
- Linux: the `.deb` installs into `/opt/PDFLion`, with `pdflion` in `/usr/bin`. Its `.desktop` file is named after `desktopName`, which Electron uses as the Wayland app ID and X11 WM_CLASS, so the dock groups the windows with the launcher, and `Exec` ends in `%F`, so file managers pass paths. `linux.mimeTypes` lists PDFLion for PDFs, rather than a `mimeType` in `fileAssociations`, which would install a MIME definition whose icon replaces the PDF icon.
- The sandbox stays on under Linux: the `.deb`'s post-install script makes `chrome-sandbox` setuid where user namespaces don't work, and installs an AppArmor profile on Ubuntu 24.04 and later. No AppImage, which can't carry a setuid helper.
- `npm run build` leaves the `.deb` out on a Mac. It's built on a Linux PC, where it can be tested.

## Tests

- `npm test` runs `node --test "test/unit/**/*.test.js"`, quoted so that Node expands the glob. Modules that unit tests import stay free of Electron, and those in `src/shared/` of Node too.
- `bridge.test.js` runs `bridge.js` in `node:vm`, after `geometry.js` and `texts.js`, with stand-ins for `window.pdflion` and `PDFViewerApplication`. When the bridge uses something new from the page, add it to the stand-ins. The test also checks that the bridge knows every `commandItem()` command in `menu.js`. `geometry.js` answers `Float32Array`s from its own realm, so its tests compare them as arrays.
- The end-to-end tests drive the dev app with Playwright, each launch with its own `--user-data-dir`. Outside CI, `launch()` loads `background.cjs` into main with Electron's `-r`: the app never activates (on macOS the `prohibited` activation policy, since macOS still activates an `accessory` app), its windows are invisible and let clicks through, and it keeps a focus of its own that `focus()`, `isFocused()`, `getFocusedWindow()` and the focus and blur events follow. `PDFLION_E2E_FOREGROUND=1` runs as CI does, with real windows and focus. `pdfs.js` writes the test PDFs, and the few that would be hard to write come from the pdf.js submodule. The suite is the safety net for pdf.js updates, so it must cover every bridge command.
- Playwright lists each tab's viewer or Home and each window's strip as pages. The helpers in `pdflion.js` find a document's page by its URL (`documentPage`), Home's once it has drawn (`homePage`), and a page's strip by its window (`stripOf`). `launch([])` starts with Home. A tab that isn't shown doesn't render, so tests open tabs one at a time. `setSize()` and `setWidth()` wait until the page has laid itself out.
- `launch()` runs the app in `en-US` (`--lang`), whatever the system's language, unless a test gives another, so that tests read the same everywhere. `texts.test.js` checks that every language has every text, naming the same values.
- `launch()` makes the first window's content 1000 × 640 (`WINDOW_SIZE`), which fits CI's smallest screen. Whatever a test points at must be in view at that size.
- `page.evaluate()` counts as a user gesture. Where user activation matters, read the page from main with `readFromMain()`.
- Playwright can't drag between windows, so `tabs.spec.js` sends the strip's messages itself.
- A key sent with `sendInputEvent()` never reaches the native menu on macOS, so there `shortcuts.spec.js` clicks the menu item itself, after checking that the page left the key alone.
- `updates.spec.js` serves a local feed (`--pdflion-update-config`), and replaces the install, which would run the downloaded bytes or dpkg: the updaters' `doInstall()`, which it reaches through `process.getBuiltinModule("node:module")`, and on macOS Squirrel.Mac (`stubSquirrel()`), which would refuse the ad-hoc-signed dev app's update.
- `test/web/` tests the web app with Playwright against `dist/web/`, which `serve-web.js` serves on port 8091, in WebKit as an iPad Pro 11 and in Chromium as a Galaxy Tab S9, both in landscape. Each test gets a persistent profile (`launchPersistentContext()`), since WebKit's default contexts store no Blobs in IndexedDB, with the locale a `test.use()` gives. The helpers in its `pdflion.js` find Home's and a document's frame, open files through the file chooser, read the library, draw with Pencil, and stub `navigator.share()`, keeping what it's given (`sharedFile()`). `backup.spec.js` reads an exported ZIP with `zip.js` itself, and writes backups with it. Stub a WebKit API on its prototype, such as `StorageManager.prototype.estimate`: WebKit may make `navigator.storage` anew, without what was set on it, once nothing holds it. `openAppExplained()` starts with the first save's explanation seen, since its modal dialog takes every press. `npm run test:web` builds the app first.
- `offline.spec.js` and `updates.spec.js` serve a build of their own on a port of their own (`serveApp()`), and note the paths asked for. `offline.spec.js` stops serving to check the app runs without the network. `updates.spec.js` builds two versions with `build()`, and replaces the served files as a release does, then has the shell check with an `online` event. `appVersion()` asks for `web/version.js`, which the service worker answers from the running version's cache. `session.spec.js` reads the stored session (`readSession()`) and the viewers whose frames are loaded (`loadedDocuments()`), and clears pdf.js's own view history before it reloads, so that the session alone restores the view. `loadBridge()` in `bridge.test.js` takes the web host's members (`host`), and a page the viewer is a frame of (`embedded`).
- `test/web/input.js` dispatches the page's own Pointer and Touch Events of pens and fingers (in WebKit through `document.createTouch()`), at shares of the part of an element in view. They don't scroll or zoom, so in Chromium it also sends trusted touches through the DevTools protocol (`Input.dispatchTouchEvent`). `pencil.spec.js`, `touch.spec.js` and `layout.spec.js` use them. `test/e2e/pen.spec.js` sends a trusted pen and fingers to a tab the same way, once `Emulation.setTouchEmulationEnabled` is on, which makes the pointer coarse and lays the toolbar out again.

- CI runs both suites on `macos-26`, `windows-2025` and `ubuntu-24.04` (the jobs `mac`, `windows` and `linux`), after a `pdfjs` job that builds pdf.js once, cached by the submodule's commit. The `web` job runs the web app's on `macos-26`, whose WebKit is closest to Safari's. The `electron` package downloads its binary on first run, so the jobs fetch it after `npm ci`. On Linux the end-to-end tests run under `xvfb-run` at 1920 × 1080, with `chrome-sandbox` setuid root, and nothing passes `--no-sandbox`. With `CI` set, Playwright also writes an HTML report, kept when a test fails, and `test.only` fails the run. The web app's suite also keeps a failed test's trace, and tries a failed test once more.

## Decisions

These were settled on purpose. Change them only on purpose.

- The bundle ID is `io.github.xlion-ch.pdflion`: `appId` in `electron-builder.yml`, and `APP_ID` in `main.js`. Changing it resets preferences and file associations. On Windows it's also the AppUserModelID, which groups the taskbar buttons with the Start menu shortcut.
- One build per Mac architecture, half the size of a universal build. Windows x64 only, which Windows on Arm runs emulated. On Linux only a `.deb` for x64, for Ubuntu 22.04 and Linux Mint 21 and later: AppImage would lose the sandbox on Ubuntu 24.04, and Flatpak and Snap bring confinement and stores of their own.
- File > New makes an untitled document in memory with one blank page: US Letter in the regions CLDR lists for it, A4 everywhere else and where the region is unknown. It counts as edited only once it changes.
- Launching without a file shows Home, rather than the Open panel. Home is a tab, every window's leftmost, an icon alone, which stays as documents open and close, so it's always a click away. A window closes with Close Window, or Close Tab on Home: macOS keeps running in the Dock, and Windows and Linux quit with the last window.
- Settings travel as one JSON file, the same on every platform and in the web app: what the user chose, not where windows were or which documents were recent. Importing adds favourites rather than replacing them.
- The web app's backup is a ZIP that Files and Finder open, with the documents under their own names, so they can be reached without PDFLion. Its entries are stored, not compressed, since PDFs mostly are already. Importing never overwrites a document: one with other changes here comes in as a copy. The desktop never opens a ZIP.
- PDFLion keeps its own recent list on every platform, since Electron's has no dates and no Linux version, and on Windows fills only once PDFs are associated with PDFLion. The thumbnails are first pages the viewer renders, which main never decodes.
- No code signing and no notarization. Every push to `main` that passes CI on all three platforms and the web app's tests is a release, so `main` takes only changes whose CI passed, after the checks by hand.
- The web app is released with the desktop app: the same commit, the same version, deployed to GitHub Pages only once the release is out, at `xlion-ch.github.io/PDFLion`, whose origin every Pages site of the account shares.
- Installed copies update themselves: in the background, installing on quit on macOS and Windows, and only with Restart Now on Linux, where installing asks for a password. Automatic checks are on until turned off. On macOS that rests on the bundle ID as the designated requirement rather than a Developer ID, and a copy downloaded from GitHub and allowed with Open Anyway updates too, with no further prompt (checked on macOS 27).
- PDFLion's own texts come in English, German, French and Italian, picked from the system's or browser's language with English as the fallback, rather than a setting of PDFLion's: the same language pdf.js picks for the viewer. Swiss German is German with "ss" for "ß". The texts are plain tables in one script, rather than Fluent like pdf.js's, so that main, the shell and the pages' classic scripts share them without a bundler.
- The viewer follows Material Design 3, as CSS over pdf.js's own UI: Material's monochrome scheme, the system font, and colours only outside forced-colors mode, which keeps pdf.js's high contrast styles.
- Page changes pdf.js can't make go through @cantoo/pdf-lib, as incremental updates, in the viewer. pdf.js's `extractPages()` would write a whole new file, without the title, page labels or password, upstream pdf-lib can't append increments, and a library in main would parse untrusted documents outside the sandbox.
- pdf.js's page tools are on, although pdf.js counts them as experimental, rather than rebuilding their selection, dragging, pasting and undo. Their changes are saved through `extractPages()`, which asks first about what it drops. Documents with a password and pure XFA forms are locked against page changes, and signed ones ask once.
- Window placement is kept in `state.json`, not with Electron's `windowStatePersistence`, which remembers each window by name and can't give a new document the last window's place.
- Tabs are PDFLion's own tab strip on all three platforms, rather than macOS's native tabs, so that the end-to-end tests on the Mac cover what Windows and Linux run. Windows have no `tabbingIdentifier`, so macOS's own tabs stay off. Tab libraries build on `<webview>`, which the security rules leave off.
- The web app keeps its own copy of each document and saves into it by itself, since Safari can't write back to the Files app, and says when the copy has changes the file in Files doesn't. Share puts a document back. It opens documents as tabs, as on the desktop.
- Once a pen has pressed on a page, only the pen draws in Pencil, Highlight and the Eraser, and fingers scroll and zoom, as on an iPad with Only Draw with Apple Pencil, also on the desktop, where it helps Surface and Wacom pens. Turning it off is remembered, and no pen turns it on again.
- A new version of the web app waits until Restart Now, or until nothing runs the old one, rather than taking over at once (`skipWaiting()`), so a running app never mixes versions, and its documents are saved first.
- The web app's library is in IndexedDB, not the origin private file system: its transactions make each save atomic, and Safari 18 reads it from the service worker. OPFS is the fallback if large files read too slowly on an iPad.
- The web app brings no dependencies: no Workbox and no bundler. Playwright, which the desktop's tests use, brings the WebKit and Chromium its tests run in.

## Known limitations

- PDFLion's own menus, labels and dialogs are in English, German, French and Italian, and English for any other language, where the viewer follows pdf.js's many languages. The German, French and Italian texts haven't been reviewed by native speakers, and none has run on Windows or Linux, whose menus' access keys were picked without trying them.
- A Mac copy run from the DMG, or from Downloads without being moved, can't update. On Linux, installing an update asks for a password, so only Restart Now installs. A copy without Check for Updates…, such as 0.1.0, never updates, and needs the latest release downloaded once.
- Undo doesn't remove an inserted page or undo a rotation, but deleting the page or rotating back does.
- The eraser's Object mode erases a whole drawing: a stroke of Pencil's, or an ink annotation from the file with all its strokes, until Line mode cuts one, which makes every stroke left of it a drawing of its own. Line mode saves a cut drawing from the file as deleted, and its pieces as new ones. Highlights go whole, also in Line mode, and only the text highlights pdf.js has as editors in ink mode. Erasing by touch or with a pen hasn't been tried on a device, nor a pen's eraser end, which the tests only imitate. Pages take `touch-action: none` only while the Eraser is on and fingers erase, so a finger's or an eraser end's drag elsewhere might scroll the page before `bridge.js` cancels it.
- The Apple Pencil's pressure, double-tap and squeeze don't reach web pages, and it has no eraser end: pdf.js's strokes have one width. Pen-only drawing, palms, hovering and long presses have run only through the tests' events, on no iPad or Surface, nor whether iPadOS rejects a palm before Safari sees it.
- After a pen has drawn with a tool, pdf.js ignores fingers in it until a tool is chosen again, so with pen-only drawing off, a finger draws only then.
- Pages moved, copied, deleted or added with pdf.js's page tools are saved as a new file, which keeps only part of the old one:

  | Change | Made by | Keeps | Loses |
  |---|---|---|---|
  | Move, copy, delete pages | `extractPages()`, from the document alone | the Info dictionary's title, author, subject and keywords, page labels, the outline, forms, the structure tree, attachments, named destinations | XMP metadata, layers (`OCProperties`), document JavaScript, viewer preferences, the open action, the page mode and layout, `Lang`, `MarkInfo`, the file IDs, valid signatures. pdf.js also sets Creator, Producer and CreationDate anew |
  | Add pages from files, or copied pages with typed form values | `extractPages()`, from several files | the outline, forms, the structure tree, attachments, named destinations | all of the above, and the Info dictionary and page labels |
  | Insert a blank page, rotate pages | @cantoo/pdf-lib, as an incremental update | everything. A signed revision stays intact, but signature checks report changes after signing | nothing, but page labels number pages by position, so an insertion shifts them |

  Copied pages with typed form values count as several files, since `withFormValues()` gives each copy its own saved copy of the document. An insertion or rotation after unsaved page changes keeps only what those keep.
- On Wayland, which Ubuntu uses by default, new windows open where the compositor puts them, and PDFLion can't see the pointer outside its windows. So a tab dropped on the desktop and a drag cancelled with Esc both tear the tab off, a second after the drag ends.
- Real drags of tabs between windows are checked only by hand.
- Shutting down Linux with unsaved changes waits for the save prompts only as long as systemd allows (`InhibitDelayMaxSec`, 5 s by default).
- Copying a whole document's text fails if pdf.js takes more than about 5 s to gather it: Chromium then asks for `clipboard-read`, which `permissions.js` denies.
- While Pencil is on, its drawings can't be selected, moved or resized, since presses go through them to draw. The Eraser takes them away.
- A backup that another app zipped again with compression is read into memory, a document at a time, as it's inflated. Backups of several GB, their Share, and reading one from Files in slices haven't been tried on an iPad. Chromium can't share a ZIP, so on Android the backup downloads.
- The web app can't save into the Files app, and isn't offered for PDFs there: documents come in through Open… or a drop, and go out through Share. PDFLion can't tell Save to Files from Mail, so any completed share counts as being in Files.
- In the web app, a tab that sleeps, and every tab after a restart, loses its undo history, as after `reopen()`. How many documents keep their frames is a guess, as is whether iPadOS keeps the app's cache and library under storage pressure.
- In the web app, saving changes made with pdf.js's page tools ends their undo, as `reopen()` does on the desktop. So they're saved only once the tab is left or the app hidden, or 30 s after the last one.
- WebKit logs a refused inline style sheet at pdf.js's hidden zoom select, under pdf.js's own CSP. Nothing visible is missing.

## Conventions

- Small modules in `src/main/`, one responsibility each, and no catch-all `utils.js`. Dev-vs-packaged paths live only in `src/main/paths.js`. A module that needs neither Electron nor Node goes into `src/shared/`, and imports nothing outside it.
- Every text PDFLion shows of its own is in `src/shared/texts.js`, by id, in each of its languages, with the values it names in braces. A new text goes into all four, which `texts.test.js` checks. Main and the shell set the language (`setLanguage()` in `i18n.js`) from Electron's locale and `navigator.languages`, and the pages' classic scripts make their own `translator(navigator.languages)`, the same language pdf.js picks. Build a text when it's shown, not at a module's load, which is before main knows the language.
- What PDFLion's alerts and prompts say is put together in `src/shared/wording.js`, from those texts. Main's modules order their buttons for each platform, and show them.
- Every third-party project PDFLion uses goes into `CREDITS` in `src/shared/credits.js` and README's Credits, with its link and licence, including what only builds or tests the app, what pdf.js or Electron brings along, and design resources. `credits.test.js` fails when the two list different links.
- Commit messages use the imperative mood and a short subject, e.g. `Add native File menu`.
